## Senior Level (5–7 Years)

### Q1: Why does a Java pod in Kubernetes crash with `Exit Code 137`, and why is there no `OutOfMemoryError` or heap dump generated?

**Answer:**
`Exit Code 137` is calculated as $128 + 9$, where 9 represents Linux signal **`SIGKILL`**.

**The Failure Mechanics**:
1. When an engineer configures `-Xmx4g` inside a container with `resources.limits.memory: 4Gi`, they fail to account for the JVM's **non-heap memory allocations**:
   $$\text{Process RSS} = \text{Heap} + \text{Metaspace} + \text{CodeCache} + \text{Thread Stacks} + \text{Direct Buffers} + \text{JVM Overhead}$$
2. While the heap stays safely below 4 GiB, Metaspace (250MB), Code Cache (240MB), 300 thread stacks (300MB), and Netty off-heap direct memory push the process's physical memory footprint (`memory.current` in cgroups v2) past the 4 GiB container boundary.
3. The **Linux kernel cgroup controller** intervenes directly, outside the JVM. The kernel invokes the **Out-Of-Memory Killer (`oom-killer`)**.
4. The kernel sends an immediate, uncatchable `SIGKILL` directly to the container process (PID 1).
5. Because `SIGKILL` terminates the process instantly at the kernel level:
   - The JVM never receives a signal it can handle.
   - No `java.lang.OutOfMemoryError` is generated by the Java runtime.
   - `-XX:+HeapDumpOnOutOfMemoryError` never triggers.
   - No shutdown hooks execute; the container simply disappears from the OS perspective.

**The Fix**:
Always use percentage-based sizing reserving a $25\%$ non-heap safety margin:
```bash
-XX:+UseContainerSupport -XX:MaxRAMPercentage=75.0
```

### Q2: How does a Kubernetes `preStop` hook prevent `502 Bad Gateway` errors during rolling deployments?

**Answer:**
During a rolling update or pod termination, two decoupled asynchronous workflows run in parallel:
1. **Control Plane Workflow**: Kubelet marks the pod as `Terminating`. The EndpointSlice controller updates endpoint slices. Kube-proxy updates iptables/IPVS rules across all worker nodes. Ingress controllers (NGINX, Envoy, Traefik) update their upstream routing tables. **This distributed network synchronization takes 2 to 8 seconds.**
2. **Local Node Workflow**: Simultaneously, the local kubelet sends `SIGTERM` to the container process.

**The Race Condition**:
If the Java application intercepts `SIGTERM` and immediately stops accepting connections or shuts down its HTTP server:
- For the next 2 to 8 seconds, Ingress controllers are still routing user requests to the pod's IP and port.
- Any client request routed during this window fails with **`502 Bad Gateway`** or **`Connection Refused`**.

**The PreStop Sleep Solution**:
```yaml
lifecycle:
  preStop:
    exec:
      command: ["/bin/sh", "-c", "sleep 15"]
```
When pod deletion begins, Kubelet executes the `preStop` hook **before** sending `SIGTERM`. During the 15-second sleep:
- The Java application remains fully operational, accepting and servicing incoming requests.
- Meanwhile, the Kubernetes control plane successfully removes the pod from all distributed Ingress and kube-proxy routing tables.
- By the time `sleep 15` finishes and `SIGTERM` is delivered, zero new requests are arriving, allowing Spring Boot's graceful drain to finish in-flight tasks cleanly.

## Staff Level (8–12 Years)

### Q3: Contrast Startup, Liveness, and Readiness probes in Kubernetes. What happens when an engineer configures the liveness probe to verify database connectivity?

**Answer:**

**The Three Probes**:
1. **Startup Probe**: Runs only at container boot. Disables liveness and readiness checks until it succeeds. Shields slow-starting Java applications (15–30s JIT boot) from premature termination.
2. **Liveness Probe**: Determines if the JVM process is alive and responsive. If it fails, Kubernetes **kills and restarts the container**.
3. **Readiness Probe**: Determines if the pod is ready to accept client traffic. If it fails, Kubernetes **removes the pod from Service endpoints and Load Balancers** without killing the container.

**The Database Liveness Anti-Pattern (The Death Spiral)**:
If an engineer points the liveness probe to Spring Boot's aggregate `/actuator/health` (which checks database connectivity):
1. A transient database hiccup, failover, or connection pool exhaustion occurs.
2. The health check returns 503 across all 50 service replicas simultaneously.
3. Because the **liveness probe** failed, Kubernetes interprets this as a fatal application crash.
4. Kubernetes **kills and restarts all 50 Java pods at the exact same moment**!
5. 50 pods reboot simultaneously:
   - JIT cache is obliterated.
   - CPU spikes to 100% across all nodes.
   - All 50 pods attempt to open new HikariCP database connections concurrently.
6. The struggling database is hit with a massive thundering herd, crashing permanently and locking the entire system into an unrecoverable **CrashLoopBackOff death spiral**.

**The Production Rule**:
- **Liveness probe** must inspect `/actuator/health/liveness` ONLY (internal JVM health).
- **Readiness probe** inspects `/actuator/health/readiness` (includes DB/external dependencies).

### Q4: Compare GraalVM Native Image vs. Project CRaC vs. AppCDS for accelerating Java cold start in Kubernetes. What are the architectural trade-offs?

**Answer:**

| Technology | Cold Start Time | Base Memory (RSS) | Peak Throughput | Dynamic Reflection / Class Loading | Operational Complexity |
|:---|:---:|:---:|:---:|:---:|:---:|
| **Standard OpenJDK 21 JIT** | 15–30 sec | 400–800 MB | **$100\%$ (Baseline)** | Unlimited | Baseline |
| **AppCDS (Class Data Sharing)** | 4–8 sec (40% faster) | 350–700 MB | **$100\%$** | Unlimited | Low (dump archive at build) |
| **GraalVM Native Image (AOT)** | **$30 - 80\text{ ms}$** | **$50 - 100\text{ MB}$** | $85\% - 95\%$ | Restricted (requires reachability metadata) | High (closed-world compilation) |
| **Project CRaC (CRIU)** | **$15 - 40\text{ ms}$** | 400–800 MB | **$100\%$ (Pre-warmed C2 JIT)** | Unlimited | Medium (CRIU capabilities + socket lifecycle hooks) |

**Architectural Selection Guide**:
- Use **AppCDS** for standard enterprise workloads where $4 - 6\text{s}$ boot is sufficient.
- Use **GraalVM Native Image** for microservices, CLI tools, and AWS Lambda where instant cold boot ($< 50\text{ms}$) and low memory footprint are paramount, and where the codebase does not rely on obscure dynamic bytecode generation.
- Use **Project CRaC** for complex, high-throughput financial or trading applications that require both **instant cold boot ($< 30\text{ms}$)** AND **full HotSpot C2 JIT peak throughput** without AOT reflection constraints.

### Q5: Explain the `ndots:5` DNS resolution penalty in Kubernetes and its impact on Java applications calling external APIs.

**Answer:**
By default, Kubernetes configures `/etc/resolv.conf` in every pod with `options ndots:5` and appends cluster search domains (`default.svc.cluster.local`, `svc.cluster.local`, `cluster.local`).

**The Mechanism**:
When an application resolves a hostname containing fewer than 5 dots (e.g. `api.stripe.com`, which has 2 dots):
1. The Linux resolver assumes the name is relative to the search domains.
2. It sequentially queries:
   - `api.stripe.com.default.svc.cluster.local` (CoreDNS $\rightarrow$ NXDOMAIN)
   - `api.stripe.com.svc.cluster.local` (CoreDNS $\rightarrow$ NXDOMAIN)
   - `api.stripe.com.cluster.local` (CoreDNS $\rightarrow$ NXDOMAIN)
   - `api.stripe.com.ec2.internal` (CoreDNS $\rightarrow$ NXDOMAIN)
   - `api.stripe.com.` (CoreDNS $\rightarrow$ Upstream $\rightarrow$ SUCCESS)
3. A single HTTP API call triggers **5 distinct UDP DNS queries** to CoreDNS!

**The Production Impact**:
At 10,000 requests/sec, this generates **50,000 DNS queries per second**. CoreDNS CPU saturates, UDP packets are dropped, and client HTTP requests experience **5-second DNS timeout stalls** (the default glibc DNS timeout).

**The Architectural Fix**:
1. In Java code, use Fully Qualified Domain Names (FQDN) with a trailing dot: `https://api.stripe.com./v1/charges`. The trailing dot informs the resolver that the domain is absolute, skipping the search path entirely.
2. Or configure `dnsConfig` in the pod spec:
   ```yaml
   dnsConfig:
     options:
       - name: ndots
         value: "2"
   ```

### Q6: Design a zero-downtime, zero-data-loss rolling upgrade pipeline for an asynchronous Java event processing service consuming from Kafka and updating PostgreSQL in Kubernetes.

**Answer — Architectural Architecture**:

```
                       [Rolling Deployment Initiated: v1 -> v2]
                                         │
       ┌─────────────────────────────────┴─────────────────────────────────┐
       ▼                                                                   ▼
┌─────────────────────────────────┐                       ┌─────────────────────────────────┐
│ Old Pod (v1) - Terminating      │                       │ New Pod (v2) - Starting         │
├─────────────────────────────────┤                       ├─────────────────────────────────┤
│ 1. Kubelet executes PreStop     │                       │ 1. Container boots on node      │
│ 2. Sets Readiness = REFUSING    │                       │ 2. StartupProbe succeeds        │
│ 3. Kafka Consumer Wakeup:       │                       │ 3. ReadinessProbe passes        │
│    `consumer.wakeup()`          │                       │ 4. Joins Kafka Consumer Group   │
│ 4. Exits poll() loop            │                       │ 5. Cooperative Sticky Assignor  │
│ 5. Completes in-flight DB tx    │                       │    migrates ONLY departed       │
│ 6. Synchronous Commit:          │                       │    partitions without full      │
│    `consumer.commitSync()`      │                       │    stop-the-world rebalance!    │
│ 7. Closes HikariCP pool         │                       │                                 │
│ 8. Clean exit (0)               │                       │                                 │
└─────────────────────────────────┘                       └─────────────────────────────────┘
```

**Key Architectural Tenets**:
1. **Cooperative Sticky Rebalance**:
   Configure `partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor`. Traditional `RangeAssignor` causes a cluster-wide "stop-the-world" consumer pause during rolling updates. Cooperative rebalance allows unaffected pods to continue processing while partitions migrate incrementally.
2. **Deterministic Shutdown Time Budget**:
   - `preStop: sleep 10`
   - In-flight worker pool drain: 20s (`awaitTermination(20, TimeUnit.SECONDS)`)
   - `consumer.commitSync()`: 5s
   - `dataSource.close()`: 5s
   - Total drain budget = $40\text{s} \le 60\text{s}$ `terminationGracePeriodSeconds`.
3. **PodDisruptionBudget (PDB)**:
   Enforce `minAvailable: 75%` to prevent simultaneous node drains from terminating too many consumer replicas.

### Q7: How do you architect a Kubernetes cluster hosting 500 Java microservices to eliminate CFS CPU quota throttling while maximizing node bin-packing and preventing noisy neighbor starvation?

**Answer — Multi-Tier Cluster Architecture**:

**1. The CPU Limit Policy**:
- **Axiom**: Never configure `resources.limits.cpu` on production Java workloads.
- Use `resources.requests.cpu` to establish strict scheduling reservations.
- This allows containers to burst into unused node CPU cycles without triggering CFS quota freezes (`nr_throttled = 0`).

**2. Standardized $1:4$ Resource Tiers**:
To achieve $> 92\%$ node bin-packing density, restrict developers to 4 standardized sizing tiers matching physical cloud instances (`m7g.4xlarge`):
- Tier Nano: `250m CPU / 1Gi RAM`
- Tier Small: `500m CPU / 2Gi RAM`
- Tier Medium: `1000m CPU / 4Gi RAM`
- Tier Large: `2000m CPU / 8Gi RAM`
This completely eliminates stranded memory or CPU capacity on worker nodes.

**3. Noisy Neighbor Protection via Kubernetes Priority Classes**:
```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: tier0-critical-payment
value: 1000000
preemptionPolicy: PreemptLowerPriority
```
If a rogue service over-consumes unreserved CPU and host node pressure rises:
- Critical Tier-0 services (payments, auth) are protected by high priority classes.
- Low-priority background workers are throttled or evicted by the kubelet.

**4. Linux Kernel CFS Period Tuning**:
On nodes hosting latency-critical workloads, tune the default Linux CFS period from 100ms down to 10ms or 20ms:
```bash
sysctl -w kernel.sched_cfs_period_us=10000
```
Shortening the period reduces the maximum freeze duration from 90ms down to 9ms, slashing P99 tail latency spikes by $90\%$.
