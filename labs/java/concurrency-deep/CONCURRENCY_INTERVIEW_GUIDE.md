## 1. Java Memory Model (JMM)

### 1.1 Happens-Before Relationships

The JMM defines a partial ordering of actions called *happens-before* (HB). If action X HB Y, then X's results are visible to Y and X occurs before Y in time.

**Rules:**

| Rule | Description |
|------|-------------|
| **Program Order** | Each action in a thread HB every subsequent action in that thread |
| **Monitor Lock** | Unlock of a monitor HB every subsequent lock of that same monitor |
| **Volatile** | Write to a volatile field HB every subsequent read of that same field |
| **Thread start()** | `Thread.start()` HB any action in the started thread |
| **Thread join()** | Any action in a thread HB `Thread.join()` returns in the caller |
| **Transitive** | If X HB Y and Y HB Z, then X HB Z |
| **Interrupt** | `Thread.interrupt()` HB detection of interrupt |
| **Finalizer** | End of constructor HB start of `finalize()` |
| **Synchronizer** | Operations on `java.util.concurrent` synchronizers establish HB |

### 1.2 Reordering, Visibility, Atomicity

**Reordering**: Compilers, JITs, and CPUs reorder instructions for optimization. Without synchronization, statements like:
```java
int a = 1;  // write
int b = 2;  // write
```
may appear reversed to another thread.

**Visibility**: Changes made by one thread to shared variables may not be visible to another thread without proper synchronization. Each thread has its own cache (L1/L2/L3), and writes may stay in cache before flushing to main memory.

**Atomicity**: Read/write on `long`/`double` without `volatile` is *not* atomic on 32-bit JVMs. For reference fields and `int` (and smaller), reads/writes are inherently atomic.

### 1.3 The `volatile` Keyword

**What it guarantees:**
- Visibility: a write to a volatile field happens-before every subsequent read
- Atomicity for 64-bit (`long`/`double`) reads/writes
- Prevents reordering with surrounding variable accesses (memory barrier insertion)

**What it does NOT guarantee:**
- NOT atomicity for compound operations (`i++`)
- NOT mutual exclusion

**Pattern: Volatile + CAS** is the foundation of lock-free programming.

**Memory barriers inserted by the JIT:**
- **StoreStore** barrier before volatile write
- **StoreLoad** barrier after volatile write (most expensive — drains store buffer)
- **LoadLoad** barrier after volatile read
- **LoadStore** barrier after volatile read

### 1.4 Final Fields and Safe Publication

**Final field guarantee:** A properly constructed object with a `final` field can be safely published without synchronization:
```java
class FinalField {
    final int x;
    FinalField(int x) { this.x = x; }
}
```
The JMM guarantees that after constructor completion, `x` is visible to all threads.

**Safe publication idioms:**
1. Static initializer (guaranteed by JVM class initialization)
2. `volatile` field or `AtomicReference`
3. `synchronized` on a well-known lock
4. Concurrent collections (`ConcurrentHashMap.put()`)
5. `final` field in a properly constructed object

### 1.5 Memory Barriers and JIT Optimization

The JIT inserts memory barriers based on the memory model. Key barriers generated by the JVM:

| Barrier | Insertion Point | Cost |
|---------|----------------|------|
| StoreLoad | After volatile write, before monitor exit | ~50-100 cycles |
| StoreStore | Before volatile write, at monitor entry | ~5-10 cycles |
| LoadLoad | After volatile read, after monitor exit | ~5-10 cycles |
| LoadStore | After volatile read, after monitor exit | ~5-10 cycles |

**JIT optimizations:**
- **Lock coarsening**: Adjacent synchronized blocks on same monitor merged
- **Lock elimination**: Escape-analyzed objects with synchronization have locks removed
- **Biased lock revocation**: When biased locking is disabled (default in Java 21+)

## 2. Synchronization Primitives

### 2.1 `synchronized`

**Monitors**: Every Java object has an intrinsic lock (monitor). The JVM uses:
- **unlocked** (no contention)
- **biased** (single-thread repeated acquisition — disabled by default in Java 21+)
- **lightweight** (CAS on lock record in stack)
- **inflated** (OS mutex/condition variable)

**Bias locking**: deprecated and disabled by default in Java 15 (JEP 374). The flag
was removed entirely in JDK 21, so `-XX:+UseBiasedLocking` no longer exists.
JEP 423 is G1 region pinning, which is unrelated.

**Lock coarsening**: If two consecutive synchronized blocks lock the same object, the JIT merges them:
```java
synchronized(this) { a++; }   // merged into one
synchronized(this) { b++; }   // merged into one
```

**Lock elimination**: If the JIT proves an object is thread-local (escape analysis), it removes synchronization entirely.

### 2.2 ReentrantLock

```java
ReentrantLock lock = new ReentrantLock(true); // fair
lock.lock();
try { /* critical section */ }
finally { lock.unlock(); }
```

**Features:**
- **Fairness**: Fair mode uses CLH queue; FIFO acquisition. Lower throughput, no starvation.
- **tryLock()**: Non-blocking attempt with optional timeout
- **lockInterruptibly()**: Allows interruption while waiting
- **Condition**: Multiple condition variables per lock (`await()`, `signal()`, `signalAll()`)

**Performance**: `synchronized` and `ReentrantLock` are comparable now. Historically (Java 5), ReentrantLock was faster. Modern synchronized uses the same CAS mechanisms.

### 2.3 ReentrantReadWriteLock vs StampedLock

**ReentrantReadWriteLock:**
- Multiple readers OR single writer
- Fairness option
- Downgrading: writer → reader
- No upgrading: reader → writer (deadlock risk)

**StampedLock** (Java 8+):
```java
StampedLock sl = new StampedLock();
long stamp = sl.readLock();   // or writeLock()
sl.unlock(stamp);
// Optimistic read (no blocking):
long stamp = sl.tryOptimisticRead();
if (sl.validate(stamp)) { /* safe to use */ }
```
- Optimistic reads are non-blocking
- Not reentrant
- No Condition support
- 10-20x faster than ReadWriteLock under low contention

### 2.4 Semaphore, CountDownLatch, CyclicBarrier, Phaser, Exchanger

**Semaphore** (counting semaphore):
- `acquire()`/`release()` — permits
- Used for resource pools (connection pool, thread pool)
- Fairness optional

**CountDownLatch** (one-shot barrier):
```java
CountDownLatch latch = new CountDownLatch(n);
latch.countDown();  // in worker threads
latch.await();      // in waiting thread
```
- Cannot be reset
- Single-use only

**CyclicBarrier** (reusable barrier):
```java
CyclicBarrier barrier = new CyclicBarrier(n, () -> System.out.println("All done!"));
barrier.await();  // each party calls this
```
- Reset via `barrier.reset()`
- Broken barrier detection

**Phaser** (flexible barrier, Java 7+):
```java
Phaser phaser = new Phaser();
phaser.register(); // or constructor(n)
phaser.arriveAndAwaitAdvance();
phaser.arriveAndDeregister();
```
- Parties can dynamically register/deregister
- Phases advance with barriers
- TreePhaser for scalability

**Exchanger**:
```java
Exchanger<Buffer> exchanger = new Exchanger<>();
Buffer buf = new Buffer();
buf = exchanger.exchange(buf); // swap buffers
```
- Used in pipeline designs
- Synchronous two-party exchange

## 3. Concurrent Collections

### 3.1 ConcurrentHashMap

**Java 7** (Segment-based):
- Concurrency level = 16 segments by default
- Each segment = independent HashMap with ReentrantLock
- `size()`: sum segment counts (may be inconsistent)
- `putIfAbsent()`: lock only target segment

**Java 8** (CAS + synchronized):
- Node array + TreeBin (when bucket > 8, TREEIFY_THRESHOLD)
- `put()` uses CAS on head node; fallback to `synchronized` on that bin
- `size()`: `sumCount()` using `CounterCell[]` (striped counters)
- ForwardNode for resize (multi-threaded transfer)

**Java 21+**:
- New epoch-based approach
- Improved table initialization
- Virtual thread friendly
- `Map.Entry` snapshot improvements

**Key methods to know:**
```java
compute(key, (k, v) -> ...);      // atomic update
computeIfAbsent(key, k -> ...);   // lazy init
merge(key, val, (v1, v2) -> ...); // merge
forEach(parallelism, pair -> ...);// parallel iteration
reduce(parallelism, (k,v)->...,(r1,r2)->...);
search(parallelism, pair -> value);
```

### 3.2 CopyOnWriteArrayList / CopyOnWriteArraySet

- Thread-safe variant where mutative operations copy the entire backing array
- `add()`: `ReentrantLock.lock()` → copy array → replace
- `get()`: no synchronization (read on volatile reference)
- Use case: listener lists, tiny mostly-read collections
- Cost: O(n) per mutation, memory pressure

### 3.3 ConcurrentLinkedQueue and ConcurrentLinkedDeque

**ConcurrentLinkedQueue** (Michael-Scott algorithm):
- Lock-free using CAS on head and tail
- `offer()`: CAS on tail
- `poll()`: CAS on head
- Wait-free contains()... not, it's O(n) with possible retries

**ConcurrentLinkedDeque**:
- CAS on both ends
- Slower than Queue due to bidirectionality

### 3.4 BlockingQueue Implementations

| Implementation | Structure | Bounded? | Fairness | Use Case |
|---------------|-----------|----------|----------|----------|
| ArrayBlockingQueue | Circular array | Yes | Optional | Bounded buffer |
| LinkedBlockingQueue | Linked nodes | Optional | No | Bounded/unbounded queue |
| PriorityBlockingQueue | Heap (array) | No | No | Priority order |
| DelayQueue | Priority + delay check | No | No | Scheduled tasks |
| SynchronousQueue | No capacity | N/A | No | Handoff (0 capacity) |
| TransferQueue (LinkedTransferQueue) | Linked nodes | No | No | Handoff with optional wait |

**SynchronousQueue** vs **TransferQueue**:
- SynchronousQueue: each insert waits for a remove (and vice versa)
- TransferQueue: `transfer()` blocks until consumed; `tryTransfer()` for non-blocking

### 3.5 ConcurrentSkipListMap / ConcurrentSkipListSet

- Sorted concurrent map/set
- Skip list implementation (layered linked list with probabilistic balancing)
- O(log n) for most operations
- No locking on reads; CAS-based writes
- SubMap, HeadMap, TailMap are view-based

## 4. Executors & Thread Pools

### 4.1 ThreadPoolExecutor In Depth

```java
ThreadPoolExecutor tpe = new ThreadPoolExecutor(
    corePoolSize,    // threads kept alive even when idle (unless allowCoreThreadTimeOut)
    maxPoolSize,     // maximum threads
    keepAliveTime,   // time excess idle threads wait before termination
    TimeUnit.SECONDS,
    workQueue,       // BlockingQueue<Runnable>
    threadFactory,   // custom thread naming/daemon
    handler          // RejectedExecutionHandler
);
```

**Thread addition logic:**
1. If running threads < corePoolSize → new thread for task
2. Else try to enqueue task in workQueue
3. If queue full and running < maxPoolSize → new thread for task
4. If queue full and running ≥ maxPoolSize → reject with handler

**RejectedExecutionHandler implementations:**
- `AbortPolicy` (default) → throws `RejectedExecutionException`
- `CallerRunsPolicy` → executes in caller's thread (back-pressure)
- `DiscardPolicy` → silently discards
- `DiscardOldestPolicy` → discards head of queue, retries

**Key tuning parameters:**
- CPU-bound: `corePoolSize ≈ Runtime.availableProcessors() + 1`
- I/O-bound: `corePoolSize = number of tasks × (1 + wait/service ratio)`

### 4.2 ForkJoinPool (Work-Stealing Pool)

**Work-stealing algorithm:**
- Each worker thread has a deque of tasks
- Workers push/pop from head (LIFO)
- Idle workers steal from tail (FIFO) of other workers
- Minimizes contention: thieves contend only at tail

**Common pool**: `ForkJoinPool.commonPool()` — used by parallel streams and `CompletableFuture`
- Default parallelism = `Runtime.availableProcessors() - 1`
- Configured via `java.util.concurrent.ForkJoinPool.common.parallelism`

**RecursiveTask vs RecursiveAction:**
```java
class SumTask extends RecursiveTask<Long> {
    if (length < THRESHOLD) return computeDirectly();
    SumTask left = new SumTask(array, lo, mid);
    SumTask right = new SumTask(array, mid, hi);
    left.fork();
    long rightResult = right.compute();
    long leftResult = left.join();
    return leftResult + rightResult;
}
```

### 4.3 ScheduledThreadPoolExecutor

- Extends `ThreadPoolExecutor` with delayed/scheduled task support
- Uses `DelayedWorkQueue` (priority queue based on next execution time)
- `schedule()`, `scheduleAtFixedRate()`, `scheduleWithFixedDelay()`
- `setRemoveOnCancelPolicy(true)` to remove cancelled tasks from queue

### 4.4 CompletionService / CompletableFuture

**CompletionService**:
```java
ExecutorCompletionService<String> ecs = new ExecutorCompletionService<>(executor);
ecs.submit(callable);
Future<String> f = ecs.take(); // returns next completed task (not submission order)
```

**CompletableFuture** (Java 8+):
```java
CompletableFuture.supplyAsync(() -> fetchData())
    .thenApply(data -> transform(data))
    .thenAccept(data -> store(data))
    .exceptionally(ex -> handleError(ex));
```

**Methods by category:**
- **Creation**: `supplyAsync`, `runAsync`, `completedFuture`
- **Mapping**: `thenApply`, `thenCompose`, `thenApplyAsync`
- **Consumption**: `thenAccept`, `thenRun`
- **Combining**: `thenCombine`, `allOf`, `anyOf`
- **Completion**: `complete`, `completeExceptionally`, `obtrudeValue`
- **Delayed**: `completeOnTimeout`, `orTimeout` (Java 9+)

**Execution note**: `thenApply` runs in the same thread as the previous stage; `thenApplyAsync` uses the common pool (or explicit executor).

### 4.5 Structured Concurrency (Java 21+)

**StructuredTaskScope**:
```java
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    Future<String> user = scope.fork(() -> fetchUser());
    Future<Order> order = scope.fork(() -> fetchOrder());
    scope.join();           // wait for all or fail
    scope.throwIfFailed();  // propagate exception
    return new Result(user.resultNow(), order.resultNow());
}
```

**ShutdownOnSuccess**: returns first successful result, cancels others
**ShutdownOnFailure**: fails if any task fails

**Benefits:**
- Tasks have clear lifetime boundaries
- Automatic cancellation on failure
- Error propagation
- Observation (thread dumps show task structure)

## 5. Virtual Threads (Project Loom)

### 5.1 How Virtual Threads Work

Virtual threads (Java 21+ preview, finalized in Java 21) are JVM-managed lightweight threads:

```
Platform Thread (Carrier)
    ├── Virtual Thread 1 (mounted)
    ├── Virtual Thread 2 (mounted)
    └── Virtual Thread 3 (suspended — continuation stored on heap)
```

**Key concepts:**
- **Carrier thread**: The OS/platform thread that executes virtual threads
- **Mount**: A virtual thread is mounted onto a carrier thread when executing
- **Unmount**: When a virtual thread blocks (I/O, park), it's unmounted and the carrier is freed
- **Continuation**: The virtual thread's stack state, stored as a `Continuation` object on the heap
- **Yield point**: A blocking operation where the virtual thread can unmount

**Implementation details:**
- `VirtualThread` implements `Thread` — backward compatible
- Stack stored in `ScopeLocal` (not native stack)
- Blocking operations (`Socket.read()`, `LockSupport.park()`) become yield points
- The JVM inserts yield points at blocking I/O operations

### 5.2 Pinning

Pinning occurs when a virtual thread cannot unmount from its carrier:

**Causes of pinning:**
1. **synchronized blocks/methods** (most common)
2. **JNI calls** (native code)
3. `Thread.yield()` inside synchronized (may still not unmount)

**Effect**: Virtual thread blocks the carrier thread temporarily; carrier cannot accept other virtual threads.

**Mitigation:**
- Use `ReentrantLock` instead of `synchronized` in frequently blocking operations
- Pool size: carrier pool should be 1× to 2× CPU cores (small!)
- Rewrite fine-grained synchronized blocks as locks

**Performance note**: Under low contention, pinning is rarely a problem. Under high contention, pinned virtual threads can degrade to platform thread behavior.

### 5.3 Virtual Threads vs Platform Threads

| Aspect | Platform Thread | Virtual Thread |
|--------|----------------|----------------|
| Creation cost | ~1 MB stack + OS thread | ~few KB (growable) |
| Context switch | ~1-10 µs (kernel) | ~0.1 µs (user-space) |
| Max count per GB | ~1000 | ~1,000,000+ |
| Blocking behavior | Blocks OS thread | Unmounts, frees carrier |
| Stack size | Fixed (default 1MB) | Growable |
| Debugging | Normal | Needs update (JDK 21+ improved) |

### 5.4 Virtual Threads with Spring Boot

**Spring Boot 3.2+** configuration:
```properties
spring.threads.virtual.enabled=true
```

**What happens:**
- Tomcat uses virtual threads for request handling (instead of platform thread pool)
- `@Async` methods use virtual threads
- No need for `WebFlux` for high concurrency

**Performance characteristics:**
- 10,000+ concurrent connections with Spring MVC
- No thread pool tuning needed
- Blocking I/O (JDBC, RestTemplate) no longer limits concurrency

**Caveats:**
- JDBC connections are still limited (100-200 pool size)
- `synchronized` in hot paths can cause pinning
- ThreadLocal usage: 10,000+ virtual threads × ThreadLocal size = memory pressure

### 5.5 Scoped Values (Java 21+)

**ScopedValue** replaces ThreadLocal for virtual threads:
```java
private static final ScopedValue<User> CURRENT_USER = ScopedValue.newInstance();

ScopedValue.where(CURRENT_USER, authenticatedUser).run(() -> {
    // Inside this scope, CURRENT_USER.get() returns authenticatedUser
    // No need to carry user through every method parameter
});
```

**Benefits over ThreadLocal:**
- Immutable binding — cannot be modified, only rebound in a new scope
- Memory: only stored for the current structured task scope
- Inherited only within the scope hierarchy (not arbitrary)

### 5.6 Structured Concurrency with Virtual Threads

```java
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    Future<Data> data = scope.fork(() -> fetchData());
    Future<Meta> meta = scope.fork(() -> fetchMeta());
    scope.join();
    scope.throwIfFailed();
    return combine(data.resultNow(), meta.resultNow());
}
```

**Key properties:**
- **Short-circuit on failure**: scope shuts down if any subtask fails
- **Cancellation propagation**: all subtasks cancelled if parent fails or times out
- **Observation**: thread dump shows hierarchical structure

### 6.1 Thread-Safe Singleton

**Approaches:**

| Approach | Thread Safety | Lazy | Performance |
|----------|--------------|------|-------------|

| synchronized getInstance() | Yes (full lock) | Yes | Worst |

| Enum | Yes (JVM guaranteed) | No | Excellent |

**Companies**: Amazon, Google, Microsoft, all

**Evaluation criteria:**
- Does the candidate know volatile is needed for DCL?
- Does the candidate mention enum singleton?
- Does the candidate discuss serialization safety?

### 6.2 Bounded Blocking Queue

```java
public class BoundedBlockingQueue<E> {
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull = lock.newCondition();
    private final Condition notEmpty = lock.newCondition();
    private final E[] items;
    private int putIndex, takeIndex, count;

    public void put(E e) throws InterruptedException {
        lock.lockInterruptibly();
        try {
            while (count == items.length) notFull.await();
            items[putIndex] = e;
            if (++putIndex == items.length) putIndex = 0;
            count++;
            notEmpty.signal();
        } finally { lock.unlock(); }
    }

    public E take() throws InterruptedException {
        lock.lockInterruptibly();
        try {
            while (count == 0) notEmpty.await();
            E e = items[takeIndex];
            items[takeIndex] = null;
            if (++takeIndex == items.length) takeIndex = 0;
            count--;
            notFull.signal();
            return e;
        } finally { lock.unlock(); }
    }
}
```

**Companies**: Amazon, Uber, DoorDash

**Evaluation criteria:**
- Proper use of `while` loops (not `if`) in condition wait
- Handling of interruptibility
- Use of `lockInterruptibly()`
- Correct `signal()` vs `signalAll()`

### 6.3 Concurrent LRU Cache

## Quick Reference: Common Pitfalls

| Pitfall | Explanation | Fix |
|---------|------------|-----|
| Publishing `this` in constructor | Object not fully constructed | Factory method or init |
| Using `double` without `volatile` | Non-atomic on 32-bit JVM | Use `volatile` or `AtomicReference` |
| `StringBuffer` in single-threaded | Synchronized overhead | Use `StringBuilder` |
| ThreadLocal memory leak | Thread pool retains ThreadLocal | Call `remove()` |
| `if` instead of `while` in condition wait | Spurious wakeup | Use `while` loop |
| `Thread.stop()` | Leaves objects in inconsistent state | Use interruption |
| Iterating CopyOnWriteArrayList in loop | May create many copies | Snapshot iterator |
| Forgetting `finally` unlock | Deadlock if exception thrown | Always unlock in `finally` |
| `ConcurrentModificationException` on HashMap | Concurrent read + structural change | Use `ConcurrentHashMap` |
