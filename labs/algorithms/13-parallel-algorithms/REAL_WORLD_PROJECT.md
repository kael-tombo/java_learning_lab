# Real-World Project: Parallel Word Histogram
> Count word frequencies in a large text with chunked threads and prove the counts exact.

## Problem
A 50 MB generated text must be histogrammed faster than the sequential baseline.
Threading bugs show up as lost or double-counted words, so exactness is the first requirement.
## Inputs
- input.txt generated by the provided script with a fixed seed (reproducible bytes).
- Thread count parameter p (1, 2, 4, 8) and a chunking strategy (equal byte ranges on line boundaries).
- Sequential baseline implementation sharing the same tokenizer.
## Steps
1. Split the file into p chunks cut only at newline boundaries so no word is split.
2. Give each thread its chunk; it builds a private hash map of word to count.
3. Join all threads, then merge the p maps by summing counts per word.
4. Sort by count descending and print the top 20 with exact totals.
5. Run the sequential version on the same file and diff the full histograms.
6. Record wall-clock milliseconds for p = 1, 2, 4, 8 in a results table.
## Acceptance criteria
- Parallel and sequential histograms are byte-identical on all 3 fixtures.
- 50 MB input reaches speedup of at least 1.5x at p = 4 on a 4+ core lab machine.
- No chunk drops or duplicates a line (line count across chunks equals file lines).
- Top-20 output matches the checked-in expected file for the fixed-seed input.
- Thread count 1 reproduces the sequential code path timings within 10 percent.
## Failure modes
- Chunks cut mid-line are prevented by the boundary rule; a validator asserts it.
- Shared-map contention is avoided by design (private maps, merge after join).
- Tiny inputs where threading overhead dominates are reported, not hidden.
## Extensions
- Parallel sort of the final histogram entries by count.
- Lock-striped shared counter variant to measure contention cost directly.
## How to demo
- Show the speedup table and state which step (map, merge, sort) dominates.
- Show the diff-empty proof of exactness between parallel and sequential runs.
